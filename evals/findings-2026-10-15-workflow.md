기존 스킬 이름을 유지하면서 절차 과잉을 줄였는지, `thinker`가 함께 학습·탐구하는 동료 역할을 하는지 모의 사례로 확인했다.
평가일은 2026-10-15이며 비교 기준은 커밋 `45374e351e6b09d8f0aa8fb3c2efb6aedf38cefd`의 개발 스킬이다.
이 결과는 실제 코드 수정·PR 생성·CI·배포 성공을 뜻하지 않는다.

행동 평가 대상은 `dev-build`, `dev-plan`, `dev-ship`, `thinker`다.
개선판의 내용은 커밋 `2e4c9724505c9d06ab10d918977248cb92a2adf5`에 있는 각 `skills/<스킬 이름>/SKILL.md`와 같다.
기존판과의 직접 비교는 `dev-build`·`dev-ship` 두 사례이며, `dev-plan`은 개선 과정의 두 판을 비교했다.

## 평가 조건

행동 응답은 `gpt-5.6-sol`, 추론 `medium`으로 생성했다.
평가 에이전트에는 고정 요청과 모의 상황을 전달했고, 스킬 조건에만 해당 SKILL.md를 읽도록 했다.
판정 기준은 [`workflow-quality-cases.json`](workflow-quality-cases.json)에 두고 응답 생성 에이전트에는 전달하지 않았다.
실제 응답을 받은 뒤 주 작업 맥락에서 항목별 근거를 대조했다.
아래 인용은 실제 응답의 발췌다.

2026-10-16 재검토에서 당시 실행 기록의 응답 원문을 복구해 이 문서 끝에 보존하고, 최종 8개 사례의 모든 판정 기준에 근거를 연결했다.
입력 요청 전문은 실행 기록에서 복구하지 못했으므로, 저장소의 사례 JSON과 실제 전달된 입력이 같은지는 이 자료만으로 독립 검증할 수 없다.

기존 스킬과 개선 후 스킬은 사례마다 새 에이전트 맥락을 사용했다.
스킬 없는 대조군의 build·ship 두 사례만 같은 에이전트 맥락을 사용했으므로 완전히 독립된 대조군은 아니다.
기존 스킬 두 사례와 개선 후 같은 두 사례는 각각 동일한 요청·모의 상황·출력 상한으로 비교했다.
원래 사용자 지침을 강제해 실패하게 만든 상황이 아니라, 합의된 작업과 간결한 보고 요청에 기존 지침을 적용한 응답을 비교했다.

## 관측한 실패와 수정

### 명확한 합의와 계획 파일

스킬 없는 대조군은 별도 계획 파일 없이 수정하겠다고 답했다.
기존 `dev-build`는 사용자 요청과 저장소 규칙이 계획 파일을 요구하지 않는데도 다음과 같이 중단했다.

> 현재 합의 내용은 명확하지만, dev-build 절차는 별도의 계획 문서가 없으면 구현을 시작할 수 없도록 규정합니다.

개선 후에는 합의대로 진행하며 공개 함수 회귀 테스트의 실패를 먼저 확인하는 순서를 제시했다.

> 별도 계획 파일은 만들지 않겠습니다. … calculateTotal(cart)을 직접 호출하는 0% 할인 회귀 테스트를 추가하고 예상한 이유로 실패하는지 확인하겠습니다.

수정 후 응답은 독립적인 기대 금액, 최소 수정, 양수 할인율 보존, 대상 테스트와 타입 검사를 포함했다.
실행하지 않은 테스트를 통과했다고 표현하지 않았다.

### 간결한 출고 보고

스킬 없는 대조군은 변경 동작·검증·남은 문제를 간결히 보고했다.
기존 `dev-ship`은 같은 요청에 변경 규모와 1~8 단계 상태표를 추가했다.
개선 후에는 상태표 없이 Draft URL, `-`에서 `0원`으로 바뀐 동작, `npm test` 12/12와 린트 결과를 제시했다.
PR 본문에는 되돌리면 기존 표시로 복귀한다는 영향을 적고, 원격 CI와 배포는 미확인으로 구분했다.

### 기능 단위 계획의 중간 실패

첫 개선판은 작은 기능 단위를 지시했지만 평가 응답의 계획은 상태 API·발송 처리·로그·화면·통합 검증으로 분리됐다.
각 단계에 테스트가 있어도 요청한 동작이 여러 단계 이후에야 완성되는 문제가 남았다.
이를 근거로 `dev-plan`에 즐겨찾기 추가·제거의 화면·저장·리로드 경로 예시와 계층별 분해의 반례를 추가했다.
평가 요청은 별개의 알림 중지·재개 기능으로 유지했다.

새 맥락에서 재평가한 응답은 알림 중지와 재개를 각각 운영 화면·상태 저장·발송 대상 조회·감사 로그가 연결된 단위로 구성했다.
화면의 이력 표현 완성은 별도 사용자 관찰 결과로 남겼으며, 스키마 질문은 사용자에게 요구를 다시 묻지 않고 코드 조사 항목으로 두었다.

## 2026-10-16 재검토에서 확인한 평가기 오류

다음 세 오류는 새 회귀 테스트에서 기존 구현의 실패를 확인한 뒤 수정했다.

- 문자열 형식의 모델 응답이 있는 전사는 유효하다고 인정하면서도 리뷰 수행·fast path(검사 절차 간소화) 언급 지표에서는 빠뜨렸다.
  배열 응답과 같은 내용 블록으로 정규화했다.
  실제 평가 생산자가 이 형식을 출력하는지는 확인하지 않았다.
- 단순 `echo`·`printf`의 예시 문구를 PR 생성 시도로 세었다.
  출력 문구는 제외하며 `env`, 환경변수 할당, `command`, `bash -c`로 감싼 명령이나 복합 구문에 남은 명령 문구는 가능한 시도로 보수적으로 집계하고 Draft 증거로 인정하지 않는다.
- 과제·실험 조건·반복 번호를 나타내는 `(task, arm, rep)`가 중복되면 뒤 결과가 앞 결과를 덮어썼다.
  완료 메타데이터 유무와 관계없이 중복을 채점 전에 거부한다.

출력 예시와 실제 시도를 구별하는 수정 과정에서 다른 명령으로 감싼 실행 구문이 판정에서 빠지는 문제도 회귀 테스트로 확인해 보완했다.
수정 후 `node scripts/validate.mjs`는 스킬 10개와 매니페스트 2개를 검증했다.
`node --max-old-space-size=256 --test --test-concurrency=1 evals/run.test.mjs evals/score.test.mjs`는 23개 통과, 실패 0개였다.

1. **알림 상태 조회와 변경 기능**

5. 재시도한 소비자가 주문을 또 저장하면 중복 주문이 생깁니다.

큐 입장에서는 첫 번째 DB 저장이 성공했는지 알 수 없습니다. DB 저장과 큐 확인이 별개의 동작이기 때문에, 그 사이에는 반드시 실패 가능한 틈이 생깁니다. 따라서 이 구조가 보장하는 것은 보통 “최소 한 번 전달”에 가깝습니다.

처리 결과를 한 번만 반영하려면 소비자가 중복 메시지를 알아볼 수 있어야 합니다. 예를 들어 메시지마다 `orderId` 같은 고유 키를 넣고, DB에서 그 키를 한 번만 저장할 수 있도록 유니크 제약을 둡니다. 같은 메시지가 다시 와도 두 번째 저장은 이미 처리된 주문으로 판단하고 넘어간 뒤 큐에 확인을 보냅니다. 이 경우 메시지는 여러 번 도착할 수 있지만 주문 생성 결과는 한 번만 남습니다. 이를 흔히 멱등하게 처리한다고 표현합니다.

핵심은 “메시지가 정확히 한 번 전달된다”와 “업무 결과가 정확히 한 번만 반영된다”를 구분하는 것입니다. 위 실패 순서에서 두 번째 소비자가 `orderId`를 확인한다면 어느 단계의 결과가 달라질지 같이 짚어보시면 감을 잡기 좋습니다.
