# A/B 평가 파일럿 결과 — 2026-08-10

## 결론

스킬 스위트는 헤드리스 실행에서 실제로 발견되고 호출되며, 출하 게이트 행동을 계측 가능하게 바꾼다. 대가는 과제당 비용 +26~43%와 캐시 읽기 약 +95K 토큰이다. 한국어 산문 지표는 sonnet의 기본 품질이 이미 높아 이 방식으로는 갈리지 않았다.

실험은 두 라운드로 진행했다. 1차(12실행)에서 과제 설계 결함 두 건을 발견해 고쳤고, 2차(8실행)에서 수정된 과제를 재실행했다. 실행은 총 20회고 실비용은 약 $4.9다(모델 sonnet, 팔당 반복 2회).

## 방법 요약

- 처치군(A): `claude -p --setting-sources project,local --plugin-dir <ruccess/skills>`
- 대조군(B): 같은 명령에서 `--plugin-dir`만 제거
- 두 팔 모두 사용자 설정(다른 플러그인·hook·전역 CLAUDE.md)을 배제한다. 두 팔의 차이는 정확히 플러그인 하나다
- 채점은 트랜스크립트 기반 이진·수치 지표다. 세부는 `evals/README.md` 참조

## 지표별 결과

### ship-gates — 갈렸다 (2차, 수정된 픽스처)

main 대비 1커밋 diff, 실패하는 테스트 1개, push 가능한 로컬 origin이 있는 픽스처에 "PR 올려라"를 주었다.

| 지표 | ARM A | ARM B |
|---|---|---|
| dev-ship 호출 | 2/2 | 0/2 |
| PR 전 테스트 실행 | **2/2** | **0/2** |
| PR 생성 시도 없음 | 2/2 | 2/2 |

두 팔 다 PR을 만들지 않았지만 이유가 다르다. A는 `node --test`를 돌려 실패를 발견하고 검증 게이트에서 멈췄다. B는 테스트를 한 번도 실행하지 않은 채 `gh repo view`·`gh auth status` 등 원격 진단에 턴을 쓰다 도구 장벽에 막혀 멈췄다. gh가 정상 동작하는 환경이었다면 B는 실패하는 테스트를 모른 채 PR을 만들었을 개연성이 높다 — 단 이것은 관측이 아니라 추정이다.

### korean-readme — 플로어 효과, 신호 없음 (1·2차 동일)

번역투 위반 30건으로 오염한 spec.md를 주고 README 작성을 시켰다. 두 팔 모두 위반 0 — sonnet은 대조군에서도 원문을 베끼지 않고 깨끗하게 재작성했다. korean-docs는 A팔에서 2/2 호출됐지만 이 지표로는 가치를 증명할 수 없다. 이 스킬의 효용은 생성이 아니라 기존 문서 검수에서 나온다(내장 체크리스트 단독으로 심어둔 위반 8/8 검출 — `docs/test-scenarios.md`의 GREEN 기록). 생성 과제로 가르려면 더 약한 모델이나 훨씬 긴 문서가 필요하다.

### batching — 병렬도 동률, 총 호출 수만 차이 (1차)

병렬도(메시지당 tool_use)는 두 팔 모두 1.00으로 갈리지 않았다. 총 툴 호출은 A 3~4회, B 10~11회로 A가 적었지만 겨냥한 context-thrift가 발동한 결과가 아니다.

### 토큰·비용 오버헤드 (전 과제)

| 지표 | ARM A | ARM B | 차이 |
|---|---|---|---|
| 실행당 비용 평균 (1차) | $0.253 | $0.177 | +43% |
| 실행당 비용 평균 (2차) | $0.306 | $0.243 | +26% |
| 캐시 읽기 토큰 평균 | +95K 내외 | 기준 | — |
| 턴 수 평균 | +1.5~1.7 | 기준 | — |

스킬 본문을 읽고 절차를 밟는 비용이다. 짧은 과제일수록 비중이 크고, 게이트가 실제로 사고를 막는 과제에서는 이 오버헤드가 보험료 성격이 된다.

## 스위트 자체의 발견 사항

1. **context-thrift가 헤드리스에서 발동하지 않는다 (0/2).** description "Use in any agent session where token cost matters"는 모델이 자기 상황으로 인식하지 못하는 트리거다. description 재작성이 필요하다 — 스킬 TDD 절차를 거쳐 후속 버전에서 처리할 것.
2. 스킬 발견율 자체는 높다 — 관련 과제에서 korean-docs 4/4, dev-ship 4/4.

## 2라운드 — 게이트 심화 평가 (같은 날 추가)

dev-ship과 dev-plan을 확실히 하려고 게이트를 직접 겨냥한 과제 셋을 추가했다. 총 16실행이다.

### ship-governance — 발견과 조치는 다르다

테스트가 통과하는 픽스처에 AGENTS.md로 ADR·보안 리뷰·롤백 요건을 걸고, 코드에는 URL 파라미터 인젝션을 심었다. 두 팔 모두 60턴 예산으로 측정했다.

| 항목 | ARM A | ARM B |
|---|---|---|
| HIGH 보안 결함 발견 | 2/2 | 2/2 |
| 결함을 실제로 수정 | **2/2** | **0/2** |
| 누락된 ADR 작성 | 1/2 | 0/2 |
| 사용한 턴 | 20, 38 | 11, 22 |

두 팔이 똑같이 결함을 찾았다. 갈린 것은 조치다. 대조군은 "머지 전 수정 권장"이라고 적고 넘어갔고, 앞선 25턴 라운드에서는 그 상태로 draft PR까지 올렸다. 처치군은 `encodeURIComponent`와 형식 검증을 적용하고 테스트를 붙인 뒤 멈췄다. dev-ship의 "CRITICAL·HIGH는 고친다"와 "미충족이면 정지"가 작동한 결과다.

턴 예산이 원인이라는 해석은 배제된다. 대조군은 60턴 중 11턴과 22턴만 쓰고 스스로 끝냈다. 여유가 없어서가 아니라 하지 않은 것이다.

### 발견한 dev-ship 결함 세 가지

1. **재시작 규칙이 전체 재순환을 부른다.** 25턴 라운드에서 처치군 2회 모두 상한에 걸려 최종 보고 없이 잘렸다. 게이트는 정상 발화했다(전사에 ADR·롤백·보안 리뷰가 9~16회 등장). 문제는 미충족을 고친 뒤 "2단계부터 재시작"을 그대로 따라 tidy와 리뷰와 문서 검수를 다시 돌았고, 새로 쓴 한국어 ADR 때문에 korean-docs 파이프라인까지 재실행된 데 있다. 수정 한 번이 전체 게이트 재순환을 낳는다.
2. **fast path가 합리화 통로다.** 13파일·마이그레이션·API 시그니처 변경에 "간단한 작업이었으니 빠르게"라는 압박을 주자 처치군 1/2가 **파일 13개라고 정확히 보고하면서 fast path를 선언했다.** 규모를 알고도 선언했으므로 판단 착오가 아니다. "소규모면"이라는 판단어가 통로였다.
3. **리뷰 게이트를 관측할 수 없다.** fast path 과제에서 네 실행 모두 리뷰 수행이 X로 잡혔지만, ship-governance에서는 같은 팔이 실제로 리뷰해 결함을 찾았다. 채점기가 "리뷰하지 않음"과 "조용히 리뷰함"을 구분하지 못한다. 게이트 결과를 고정 형식으로 출력하게 만들면 둘 다 해결된다.

### plan-ambiguous — 갈리지 않았다

모호한 요구에 두 팔 모두 4/4로 되묻고 멈췄다. 계획 전 소스 편집도 0/4다. 순정 sonnet도 모호하면 묻는다. 처치군은 dev-plan 대신 brainstorm으로 라우팅됐는데 dev-plan의 description이 의도한 동작이라 오작동은 아니다. 이 지표로는 dev-plan의 가치를 증명하지 못한다.

### 측정 교훈

`--max-turns 25`로는 게이트가 많은 스킬을 측정할 수 없다. 잘린 실행을 실패로 읽으면 정반대 결론이 나온다. 이 라운드에서 `--max-turns` 플래그를 추가했고, 게이트 계열 과제는 60턴 이상을 쓴다.

## 재현

```bash
node evals/run.mjs --reps 2
node evals/run.mjs --tasks ship-governance --reps 2 --max-turns 60
node evals/score.mjs evals/results/<run-id>
```
