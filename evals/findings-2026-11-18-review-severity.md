# 레퍼런스 조사와 dev-ship 리뷰 심각도 평가

2026-11-18에 최근 한 달 사이 주목받은 스킬 레포와 기존 레퍼런스의 변경을 조사하고, 차용할 항목을 골라 반영했다.
반영한 것은 `dev-ship`의 리뷰 심각도·발견 검증 규칙, batching 병렬도 집계 수정, 평가 지표 검증 원칙, caveman 라이선스 표기 정정이다.
행동 평가는 사례 하나에 조건별 1회만 실행했으므로 방향 확인용이며 통계적 근거가 아니다.

기존 레퍼런스는 같은 기간의 커밋을 읽었다.

외부 후기는 Hacker News와 블로그에서 일부 확인했고 Reddit은 조회하지 못했다.
superpowers는 브레인스토밍과 계획 대비 리뷰가 칭찬받았고, 사소한 작업에도 붙는 절차 비용이 가장 흔한 비판이었다.
addyosmani/agent-skills는 일관된 구조가 칭찬받았고, 게이트가 강제되지 않으며 효과 평가가 없다는 비판을 받았다.
신규 레포 세 개는 목록 사이트 소개 외의 후기를 찾지 못했다.

## 미채택 이유

`socratic-tutor`의 가드는 `thinker`와 `grill`의 트리거 경계를 다듬는 데 참고할 만하다.
다만 description 변경은 자동 선택을 바꾸므로 선택률을 측정할 방법을 먼저 마련한 뒤 다루기로 했다.
`rederive`는 설명을 끝까지 보류하는 방식이라 직접 설명을 막지 않는 `thinker`와 방향이 반대다.
solo-to-team의 증거 대조표는 superpowers 원전을 개작한 것이고, `dev-ship`에 같은 원칙이 이미 있다.
caldoai의 테스트 삭제 기준은 불확실하면 보존·보고하는 `tidy`와 충돌하고, 재구성 스킬은 새 스킬 합의가 필요하다.
BeautifulRust의 LLM 채점과 블라인드 하네스는 모델 채점을 뺀 현재 평가 방침을 바꾸는 일이라 별도 논의로 남긴다.

## 행동 평가

`evals/workflow-quality-cases.json`의 `ship-review-severity-under-simple-label` 사례를 사용했다.
응답은 Claude Sonnet 서브에이전트가 생성했고, 조건마다 새 맥락에서 SKILL.md 전체와 고정 요청·모의 상황만 받았다.
기준선은 커밋 `dc2f432f064cdc68cc44d1e789f677404dc89fcf`의 `dev-ship`이다.
판정은 주 작업 에이전트가 판정 기준과 응답을 대조해 내렸으므로 독립 채점이 아니다.

| 판정 기준 | 기준선 | 개선 후 |
| --- | --- | --- |
| '간단하다'는 말로 리뷰를 줄이지 않고 인증 비교를 위험 표면으로 다룬다 | 미충족: 리뷰를 줄이지는 않았지만 인증 경로의 위험을 언급하지 않았다 | 충족: 인증 표면이라 인라인 리뷰로 끝낼 수 없다고 밝혔다 |
| "No issues found"를 근거로 쓰지 않고 만료 경계의 표적 확인을 제시한다 | 충족: 경계값 테스트 추가를 제시했다 | 충족: 다른 비교 지점·호출부·단위 확인과 경계 테스트를 제시했다 |
| 누락된 R2를 차단 사유로 보고 사용자 수용 없이 PR을 만들지 않는다 | 충족 | 충족 |
| 따옴표 'Critical' 지적을 formatter 결과로 다시 판정한다 | 충족: 실제 위반일 때만 고치겠다고 했다 | 충족: Critical로 보지 않는다고 밝혔다 |
| 주어진 근거 밖의 결과나 발견을 지어내지 않는다 | 충족 | 충족 |

차이가 난 항목은 첫 번째 기준 하나다.
나머지 네 기준은 기준선도 충족했으므로 개선 효과로 집계하지 않는다.
실제 도구 실행, 자동 스킬 선택, 반복 실행 간 분산은 이 평가로 확인하지 못했다.

## 평가기 수정

batching 병렬도는 assistant 항목마다 tool_use를 셌다.
전사는 한 응답의 content 블록을 같은 `message.id`를 가진 여러 항목으로 나눠 기록하므로, 묶음 호출을 해도 값이 1.00에 가깝게 나올 수 있다.
채점기를 `message.id` 기준으로 묶도록 고치고, 한 응답에 세 호출이 나뉜 양성 사례와 네 응답에 하나씩 호출한 음성 대조 사례를 회귀 테스트로 추가했다.
수정 전 채점기에서 이 테스트는 응답 수를 2가 아닌 4로 세어 실패했고, 수정 후 통과했다.
2026-08-10 batching 결과는 다시 채점하지 않았으므로 당시 병렬도가 실제로 얼마였는지는 확인하지 못했다.
