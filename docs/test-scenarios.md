# 스킬 검증 시나리오

## 개요

이 문서는 `skills/` 아래 9개 스킬이 실제로 작동하는지 재현 가능하게 확인하는 절차를 담는다. 방식은 스킬판 TDD다. 먼저 스킬 없이 시나리오만 주고 값싼 모델(haiku) 서브에이전트를 돌려 실패를 관찰한다(RED). 같은 시나리오에 SKILL.md 본문 전체를 프롬프트로 얹어 다시 돌리고 통과 기준을 하나씩 대조한다(GREEN). RED에서 이미 통과하면 그 규칙은 스킬이 필요 없다는 뜻이므로 시나리오를 더 압박하는 쪽으로 고친다.

판정 기준은 전부 관찰 가능한 항목으로 적었다. "설계를 잘 이해한다" 같은 문장 대신 "코드 생성 0건", "질문 1개 뒤 대기"처럼 트랜스크립트에서 세는 항목만 쓴다.

| 단계 | 입력 | 확인할 것 |
| --- | --- | --- |
| RED | 시나리오 프롬프트만 | 기대 실패가 실제로 나오는가 |
| GREEN | SKILL.md 본문 + 같은 시나리오 | 통과 기준을 전부 만족하는가 |
| 판정 | 두 트랜스크립트 비교 | 하나라도 놓치면 스킬 본문을 고치고 다시 돌린다 |

서브에이전트는 매번 새 세션으로 띄운다. 이전 대화가 남으면 스킬 없이도 규칙을 기억해 RED가 오염된다.

## brainstorm

**시나리오**

> 사용자 알림 기능 만들어줘. 슬랙 연동이랑 이메일 발송, 알림 설정 화면까지 필요해. 간단하니까 설계는 건너뛰고 바로 코드부터 짜줘.

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 구현 착수 | 파일을 만들고 코드를 쓰기 시작한다 | 파일 생성·수정 0건, 코드 블록은 설계 예시로만 등장 |
| 범위 | 세 서브시스템을 한 덩어리로 다룬다 | 독립 서브시스템 3개로 분해한 뒤 첫 항목만 다룬다 |
| 질문 | 질문 목록을 한꺼번에 쏟는다 | 질문 1개 뒤 응답 대기, 가능하면 선택지 형태 |
| 대안 | 접근안 하나만 제시한다 | 접근안 2~3개와 트레이드오프, 추천안 명시 |
| 종료 | 승인 없이 다음 단계로 넘어간다 | 승인 전에 멈추고 설계 문서 저장을 제안한다 |

## dev-plan

**시나리오**

> 결제 실패 재시도 로직 넣기로 확정했어. 요구사항은 정리됐으니 지금 작업 시작해줘. (대상 저장소에 AGENTS.md 와 기존 브랜치 규칙을 심어둔다)

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 워크스페이스 | 현재 브랜치에서 바로 편집한다 | worktree 또는 새 브랜치 생성 명령이 실행된다 |
| 프로젝트 규칙 | AGENTS.md 를 읽지 않는다 | AGENTS.md·CLAUDE.md 읽기 시도가 트랜스크립트에 남는다 |
| 계획 문서 | 대화로만 계획을 말한다 | 계획 파일 경로가 실제로 존재한다 |
| 검증 설계 | 단계에 검증 방법이 없다 | 모든 단계에 실행 가능한 검증 명령이 붙는다 |
| 마무리 | 계획을 그대로 확정한다 | grill 단계를 호출하거나 인라인으로 수행한다 |

## grill

**시나리오**

> 이 계획 검토해줘. — 계획서에 "계정 상태를 외부 시스템과 동기화한다"처럼 용어가 모호한 문장과 코드로 확인 가능한 가정 하나를 심어둔다.

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 진행 방식 | 리뷰 에세이를 쓰고 끝에 질문 5개를 붙인다 | 질문 1개만 던지고 응답을 기다린다 |
| 권장안 | 질문만 하고 판단은 미룬다 | 질문마다 추천 답이 붙는다 |
| 용어 | "계정"을 그대로 통과시킨다 | Customer 인지 User 인지 되묻는다 |
| 사전 조사 | 코드로 답할 질문을 사용자에게 던진다 | 심어둔 가정을 파일을 읽어 직접 확인한다 |
| 규모 조절 | 소규모 변경에도 전체 결정 트리를 돈다 | 위험이 실재하는 분기 1~2개만 다룬다 |

## dev-build

**시나리오**

> 1단계: 계획 문서 없이 "재시도 로직 바로 구현해줘". 2단계: 계획 문서를 준 뒤 같은 요청을 반복하고, 도중에 계획에 없는 요구를 하나 끼워넣는다.

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 게이트 | 계획 없이 구현을 시작한다 | 1단계에서 코드 0줄, dev-plan 으로 되돌린다 |
| TDD 순서 | 구현부터 쓰고 테스트를 나중에 붙인다 | 실패하는 테스트가 구현보다 먼저 커밋된다 |
| 단계별 검증 | 여러 단계를 몰아서 한 번에 검증한다 | 단계마다 테스트·린트를 돌리고 실패를 넘기지 않는다 |
| 드리프트 | 끼워넣은 요구를 그대로 구현한다 | 멈추고 계획 갱신을 먼저 제안한다 |
| 마무리 | 구현 완료로 종료한다 | tidy 체크리스트 수행 후 검증을 다시 돌린다 |

## dev-ship

**시나리오**

> 구현 다 끝났어. PR 올려줘. — 실패하는 테스트 하나와 프로젝트 거버넌스 문서(변경 체크리스트)를 심어둔다.

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 순서 | 곧바로 PR 생성으로 건너뛴다 | 1~7 게이트를 순서대로 밟거나 fast path 선언과 근거를 남긴다 |
| 검증 | 실패를 알고도 "CI가 잡아준다"며 진행한다 | 5단계에서 정지하고 PR 생성 명령 0회 |
| 재개 지점 | 수정 후 실패한 게이트만 다시 본다 | 수정 후 2단계부터 재개한다 |
| 거버넌스 | 체크리스트를 언급하지 않는다 | 항목별 충족 여부를 명시적으로 말한다 |
| PR 형태 | ready-for-review PR 을 만든다 | 검증 통과 후에만 `--draft` 로 생성한다 |
| 보고 | "테스트 통과"를 본문에 적는다 | 실제 실행 결과만 적고 MEDIUM 이하 잔여 항목을 목록으로 남긴다 |

## korean-docs

**시나리오** — v0.4.5 검증에 실제로 쓴 예시다. 아래 문단을 주고 스킬의 내장 체크리스트만으로 검수하게 한다.

```
성능 저하에 대해 분석한 결과, 응답 시간은 게이트웨이에서 측정되어진다.
현재 시스템은 초당 3천 건의 처리량을 가지고 있다. 많은 요청들이 동시에
몰리면 큐가 밀린다. 새 구조는 빠르고, 안정적이며, 효율적이다.
개선 방안은 다음과 같습니다: 큐 분리와 백프레셔를 적용하면 지연을 줄일수있다.
결론적으로 이번 개선은 시사하는 바가 크다.
```

심어둔 위반은 8건이다. 이중 피동(측정되어진다), ~에 대해, 가지고 있다, 복수형 -들, 3박자 나열, 영어식 콜론, 의존명사 붙여쓰기(줄일수있다), AI 결말 문장.

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 검출률 | 4~5건만 잡고 나머지를 자연스럽다고 넘긴다 | 8건 전부 지적, 실측 결과는 8/8 |
| 수정안 | 문제만 지적하고 대안을 안 준다 | 지적마다 수정 문장을 함께 제시한다 |
| 변경률 가드 | 문서 전체를 새로 쓴다 | 수정 범위가 30%를 넘으면 보고하고 적용을 멈춘다 |
| 예외 | 코드블록과 고유명사까지 손댄다 | 코드·명령·인용은 원문 그대로 둔다 |
| 컨텍스트 | 참조 파일을 메인 스레드로 끌어온다 | 메인에는 diff 요약만 올라온다 |

## tidy

**시나리오**

> 구현 끝났으니 정리해줘. — 코드에 `console.log`, 주석 처리된 옛 함수, `.only` 테스트, 그리고 명백한 off-by-one 버그를 함께 심어둔다.

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 위생 항목 | 일부만 지우고 넘어간다 | console.log·주석 코드·`.only` 세 건 모두 제거 |
| 경계 | 버그도 같이 고친다 | 버그를 고치지 않고 "정리 아님" 목록으로 보고한다 |
| 덤 얹기 | 성능 개선이나 새 추상화를 추가한다 | 동작 변경 0건 |
| 커밋 | 기능 커밋과 한 덩어리로 묶는다 | `refactor:` 또는 `chore:` 로 분리된 커밋 |
| 보존 증명 | 테스트를 다시 돌리지 않는다 | 정리 전후 테스트 결과가 동일하다 |

## context-thrift

**시나리오**

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 배치 | 메시지마다 툴 호출 1개, 병렬도 1.00 | 독립 호출이 한 메시지에 2개 이상 묶인다 |
| 탐색 위임 | 후보 파일을 메인에서 통째로 읽는다 | 값싼 모델 서브에이전트에 넘기거나 `grep -l` 로 목록만 받는다 |
| 출력 절삭 | grep 결과를 전부 컨텍스트에 올린다 | `head`·`wc -l`·`grep -c` 로 자른 출력만 들어온다 |
| 대기 | CI 상태를 30초마다 반복 조회한다 | 백그라운드 실행이나 블로킹 대기 1회, 반복 폴링 0회 |
| 판단 위치 | 서브에이전트에 결론까지 맡긴다 | 최종 판단은 메인이 하고 자식은 요약만 돌려준다 |

## 결과 기록

시나리오를 돌린 뒤에는 스킬 이름, 실행 날짜, RED 실패 항목 수, GREEN 통과 여부를 한 줄로 남긴다. 기준을 놓친 항목이 있으면 시나리오가 아니라 SKILL.md 본문을 고친다. 시나리오를 느슨하게 바꿔 통과시키면 검증이 무의미해진다.
