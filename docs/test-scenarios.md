# 스킬 검증 시나리오

## 개요

이 문서는 `skills/` 아래 9개 스킬의 효과와 보존해야 할 동작을 확인하는 절차를 담는다.
새 규칙의 도입 효과를 검증할 때는 스킬 없는 기준선의 실패를 관찰하고(RED), 같은 시나리오에 SKILL.md 전체를 적용해 실패가 해소되는지 확인한다(GREEN).
기존 스킬의 문제를 수정할 때는 변경 전후 스킬도 같은 요청으로 비교한다.
기준선이 이미 통과하면 그 결과를 그대로 기록하고 해당 항목의 개선 효과를 주장하지 않는다.
수치·불확실성·말투 같은 보존 회귀는 기준선이 통과해도 유효하며, 실패를 만들려고 고정된 요청이나 판정 기준을 바꾸지 않는다.

판정 기준은 실제 응답과 실행 기록에서 확인할 수 있도록 적는다.
도구 동작은 "코드 생성 0건", "질문 1개 뒤 대기"처럼 확인하고, 자연스러움과 설명의 충분함은 실제 문장을 읽고 판정 이유를 남긴다.

| 단계 | 입력 | 확인할 것 |
| --- | --- | --- |
| RED | 시나리오 프롬프트만 | 도입 효과를 입증할 실패가 실제로 있는가 |
| GREEN | SKILL.md 본문 + 같은 시나리오 | 통과 기준을 전부 만족하는가 |
| 판정 | 두 트랜스크립트 비교 | 실패 수정과 보존 회귀를 구분하고, 필요한 기준을 놓치면 원인을 확인해 수정한다 |

서브에이전트는 매번 새 세션으로 띄운다. 이전 대화가 남으면 스킬 없이도 규칙을 기억해 RED가 오염된다.

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 구현 착수 | 파일을 만들고 코드를 쓰기 시작한다 | 파일 생성·수정 0건, 코드 블록은 설계 예시로만 등장 |
| 범위 | 세 서브시스템을 한 덩어리로 다룬다 | 세 서브시스템의 경계와 의존성을 구분하고 미정 선택을 다루되 요청 범위를 누락하지 않는다 |

| 종료 | 승인 없이 다음 단계로 넘어간다 | 승인 전에 멈추고 설계 문서 저장을 제안한다 |

## korean-chat

**시나리오**

> 어제 장애 원인 팀에 공유할 슬랙 메시지 써줘. 명사형으로 작성해 줘. — 원본 노트: `cache stampede`, `no lock on miss`, `5 min`, `320 DB connections exhausted`, `DB_CONNECTION_EXHAUSTED`.

| 항목 | 기대 실패(RED) | 기대 통과(GREEN) |
| --- | --- | --- |
| 도입부 | "안녕하세요, 공유드립니다"로 시작한다 | 첫 줄이 명사형 결론 한 문장, 인사말 0회 |
| 종결 | 명시한 말투 요청을 무시한다 | 이 메시지는 요청한 명사형으로 쓴다. 일반 대화의 기본은 존댓말이며 보고의 말투를 다른 응답에 전파하지 않는다 |
| 본문 | 줄글 문단으로 늘어놓는다 | 병렬 사실은 "항목: 내용" 형태의 개조식 불릿이며, 인사·빈 헤징·재진술·예고성 설명은 없다. 의미 있는 불확실성과 확인된 작업 상태는 보존한다 |
| 보존 | 정확 식별자·토큰을 바꾸거나 no-lock 부정 사실을 생략·중복한다 | `cache stampede`·`5 min`·`320`·`DB_CONNECTION_EXHAUSTED`를 정확히 보존하고, no-lock 부정 사실은 `no lock on miss` 또는 `캐시 미스 시 락이 없음`으로 정확히 1회 보존 |
| 문장 조각 | "인증 미들웨어. 버그. 수정 필요."처럼 조사를 떼어낸다 | 조사 탈락 0회, 조사와 어미가 살아 있는 문법적 한국어 문장 |
| 자연스러움 | 특정 표현의 유무만으로 품질을 판정하거나 의미를 삭제한다 | 이중 피동과 불필요한 상투어를 문맥에서 고치고 자연스러운 표현과 필요한 의미는 보존한다 |

### 설명·말투·의미 보존 회귀

[`evals/korean-quality-cases.json`](../evals/korean-quality-cases.json)에 고정된 다섯 요청과 판정 기준을 둔다.
이 파일은 수동 행동 평가용이며 `evals/run.mjs`의 자동 실행 과제가 아니다.
스킬 없는 기준선에는 사례의 prompt만, 스킬 조건에는 해당 SKILL.md 전체와 같은 prompt를 평가 에이전트에 전달한다.
checks는 판정 기준으로 사용하고, 실제 응답과 항목별 통과 여부·이유를 기록한다.
재현할 때는 모델과 추론 설정을 고정하고 조건과 사례마다 새 평가 맥락을 사용한다.
기존 결과가 여러 사례를 같은 맥락에서 실행했다면 그 제한을 결과에 명시한다.
각 사례의 말투 요청은 다른 사례로 넘기지 않는다.
평가자는 실제 응답과 항목별 판정 이유를 남기고, 주 에이전트가 응답을 직접 확인한다.
2026-10-15 평가의 변경 전 스킬은 커밋 `45374e3`이며, 모델은 gpt-6-luna, 추론 설정은 medium이다.
`git show 45374e3:skills/korean-chat/SKILL.md`와 `git show 45374e3:skills/korean-docs/SKILL.md`로 변경 전 본문을 얻는다.
변경 후 본문은 이 저장소의 `skills/korean-chat/SKILL.md`와 `skills/korean-docs/SKILL.md`를 사용한다.

| 사례 | 확인할 행동 |
| --- | --- |
| chat-beginner | 짧은 초보자 질문에 존댓말로 뜻·이유·구체적인 예시를 설명한다 |
| chat-status | 테스트·운영 배포·실제 측정을 구분하고 소요 시간을 지어내지 않는다 |
| chat-requested-register | 명사형 세 줄 요청을 따르고 사실을 보존한다 |
| docs-beginner | 비개발자에게 중복 주문의 원인과 개선안을 기본 서술형으로 설명하고 미구현 상태를 보존한다 |
| docs-fidelity | 기본 서술형을 쓰며 가능성·예측·수치·식별자·서로 다른 속성을 보존한다 |

말투 적합성, 설명의 충분함, 사실과 주장 강도의 보존, 자연스러움을 따로 확인한다.
후보 표현의 개수는 실제 오류 개수나 한국어 품질 점수로 해석하지 않는다.
기준선도 통과한 항목은 개선 효과로 집계하지 않고, 작은 표본의 통과를 반복 실행의 보장으로 확대하지 않는다.

### 행동과 작업 상태

변경 전 스킬과 변경 후 스킬을 각각 새 에이전트에 주고 아래 요청에 답하게 한다.
형식상 다음 행동 줄이 없다는 이유만으로 실패로 판정하지 않는다.
독자가 할 일이 이미 명확하거나 답변이 완결됐다면 추가 행동은 필요 없다.

| 시나리오 | 통과 기준 |
| --- | --- |
| 토큰 교체는 끝났고 재시도 테스트가 실패했어요. 확인된 원인은 만료 토큰 fixture고 운영 배포는 아직 안 했어요. 제가 직접 고치려면 어떻게 해야 해요? | 수정 행동을 먼저 제시하고 절차를 번호로 나눈다. 테스트 통과나 운영 배포를 완료했다고 쓰지 않는다 |
| 검토할 선택지는 Redis, DB 락, 큐 세 가지예요. 중복 실행 방지가 목적이고 새 인프라 운영은 피하고 싶어요. 각각 비교해서 추천해 주세요. | 추천을 먼저 제시하고 세 선택지의 장단점을 보존한다. 끝에서 새 정보 없이 같은 결론을 반복하거나 불필요한 행동을 만들지 않는다 |
| 원인을 아직 못 찾았고 테스트 시간도 몰라요. 어디까지 됐고 얼마나 걸려요? | 원인과 시간이 미확정임을 밝힌다. 미확인 상태를 완료 성과로 표시하거나 시간을 지어내지 않는다 |
| 다음 여덟 항목을 모두 설명해 주세요: 인증, 인가, 입력 검증, 멱등성, 재시도, 타임아웃, 로깅, 롤백. 존댓말로 써 주세요. | 항목을 묶더라도 여덟 개를 모두 설명하고 존댓말을 따른다 |

2026-09-21 변경 전 스킬 평가에서 절차 번호와 시간 불확실성은 이미 보존됐다.
다만 비교 응답은 추천 결론을 반복했고, 상태 응답은 `완료: 원인 확인 전 단계임.`이라고 써서 미확인 상태를 완료 항목에 넣었다.
변경 후 새 에이전트 평가에서는 같은 세 요청에서 번호 절차와 시간 불확실성을 보존했고, 미확인 상태를 완료 항목에 넣지 않았다.
비교 응답의 마지막 문단은 추천을 다시 언급했지만 트랜잭션 범위와 장시간 작업 조건을 추가했다.
추가 요청에서는 여덟 항목과 존댓말을 모두 보존했으나 목록을 나누지는 않았다.
묶음 구성은 권장 사항으로 평가하며, 요청한 항목의 누락 여부와 구분한다.

## v0.9.1 호출 범위와 의미 보존 회귀

도구 사용을 끈 Claude Haiku에 같은 질문을 주고 스킬 없음·수정 전·수정 후 응답을 비교한다.
수정 전 스킬은 변경 전에 별도로 보관하고, 각 실행은 새 세션에서 시작한다.
이 검사는 규칙 해석만 확인하며 실제 파일 변경·자동 호출·전체 PR 작업을 검증하지 않는다.

| 질문 | 통과 기준 |
| --- | --- |
| API 호출 세 개를 묶으면 총비용이 항상 ⅔ 줄어드는가? | 총비용 절감을 보장하지 않고 캐시·요금·모델 왕복 조건을 구분한다 |
| 이미 승인된 구체 설계를 구현할 때 다시 승인받아야 하는가? | 합의한 범위 안에서는 재승인을 요구하지 않는다 |

| 인증 조건을 한 파일에서 다섯 줄 바꾸면 PR의 빠른 경로를 적용하는가? | 변경 줄 수와 무관하게 전체 경로를 적용하고 저장소 거버넌스를 확인한다 |
| `최적화하면 효율을 높일 수 있다. 매출이 증가할 것이다.`를 교정하면? | 조건·가능성·미래 예측을 보존하고 현재 사실로 단정하지 않는다 |

수정 전 스킬을 넣은 응답은 인증 변경을 빠른 경로 대상으로 판단했고, 수정 후에는 제외했다.
